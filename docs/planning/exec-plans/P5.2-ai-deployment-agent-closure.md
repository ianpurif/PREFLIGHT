# P5.2 — AI Deployment Agent Closure

## Outcome

A narrow tool-calling deployment agent can resolve one public deployment request, inspect the
corresponding public evaluation and live Sepolia clearance state, and prepare the exact existing P5
release request. A host-owned state machine derives every security result. The model cannot choose
canonical bindings: the host resolves a finite public catalog form before provider use and requires
the first model call to echo that same entry. The model cannot mutate registry state, sign, call
release consumption, or declare a release authorized. Eligible attempts stop at the browser Ledger
boundary; only an existing, cryptographically verified P5 `ReleaseAuthorization` can later change
the recorded status to `AUTHORIZED`.

## Non-goals

- P6 UI, digital twin, robot activation, or autonomous execution
- changes to P1–P5.1 protocol, evaluator, CRE, registry, EIP-712, nonce, Ledger, or Speculos semantics
- a general chatbot, open-ended tool framework, registry writer, signing tool, or backend key custody
- creating a live Sepolia clearance or claiming physical Ledger, Secure Element, or Clear Signing proof
- Ledger Key Ring or `wallet-cli ring`

## Invariants

- The host accepts only finite public forms generated from catalog aliases, discards raw text, and
  gives the model/audit only a canonical public projection.
- A deterministic catalog resolves the request before provider use to one immutable canonical
  site/robot/build tuple; the first model aliases must resolve to that same entry, and the signer
  comes from trusted operator context, never model output.
- Tool order is fixed and bounded. Unknown, malformed, skipped, repeated, reordered, or oversized calls
  fail closed before Ledger.
- Public evaluation/clearance inspection is informative; only `ReleaseService.prepare()` decides whether
  an intent may be issued and therefore preserves live P4 checks, exact bindings, signer policy, and nonce.
- The agent exposes no generic network, shell, filesystem, registry-write, signing, signature, consume, or
  arbitrary-chain capability.
- Model prose never controls `BLOCKED`, `LEDGER_APPROVAL_REQUIRED`, or `AUTHORIZED`.
- Ledger signing remains explicit browser/user action over production WebHID or development/test Speculos.
- `AUTHORIZED` is reported only after reading the exact consumed nonce and validating the stored P5
  `ReleaseAuthorization` against the prepared intent and digests.
- Audit output contains only a host-generated public request, exact bindings, ordered tools, stable
  policy codes, intent digests, Ledger boundary state, and final state; it excludes raw submitted
  text/prompts/model output, raw signatures, credentials, confidential envelopes, blinds, CRE
  payloads, and private evaluation details.

## Change surfaces

- `apps/api/src/agent/**`: deterministic controller, strict tool schemas, public catalog, provider boundary,
  real provider adapter, authorization-status reader, and public audit record
- `apps/api/src/release/**`: read-only exact nonce authorization-status seam; no nonce or consume redesign
- `apps/api/src/server.ts` / `src/index.ts`: narrow prepare/status agent routes and optional environment wiring
- `apps/api/test/**`: orchestration, adversarial, provider-contract, status, leakage, and route tests
- `.env.example` / `turbo.json`: ignored provider/catalog configuration names only
- scaffold verification and P5.2 planning, architecture, security, partner, evidence, AI-use, and verification docs

## Acceptance checks

- A catalog-generated natural-language Build B form resolves locally to exact public canonical
  identifiers and invokes the required tools once in order; real deterministic preparation returns
  `LEDGER_APPROVAL_REQUIRED` and one exact P5 request.
- Unsafe, missing, expired, revoked, and mutated exact-build attempts stop before a Ledger request with stable
  deterministic reasons; conflicting model claims cannot change the result.
- Mainnet/alternate registry, alternate/conflicting target, non-catalog private-context text,
  arbitrary payload, signature/nonce reuse, skip-Ledger, registry mutation, unknown tools,
  prompt/tool injection, and fabricated authorization all fail closed.
- Different provider wording/transcripts produce the same security target and result.
- A consumed authorization produced through actual P5 signature recovery/postcheck/atomic nonce consumption
  is the only positive authorization-status case.
- Real provider configuration has no test fallback, sends strict function schemas,
  bounds turns/output, and never places its key in body, audit, error, or model-visible context.
- Live positive Sepolia evidence is not claimed: the currently documented registry fixture is unregistered.

## Parallel work / worktrees

Read-only specialists reviewed architecture, implementation seams, adversarial tests, and Ledger partner
eligibility. The primary agent owns every write in this working tree. An independent read-only review
found a conflicting-target alias-containment gap and raw request disclosure risk; both were remediated
with the finite public grammar, raw-text discard, and exact host/model target check.

## Risks and rollback

- Provider nondeterminism is contained by a fixed state machine and exact schemas; provider failure blocks.
- The deployed P4 registry is non-enumerable, so a trusted public catalog must supply the complete candidate
  clearance. Ambiguous or absent entries block; the model cannot construct a clearance.
- There is no documented live positive Sepolia clearance for Build B. Positive tests/evidence use a clearly
  labeled deterministic registry reader; live access can truthfully demonstrate the missing/blocked state.
- P5 replay protection remains coordinated by one SQLite database. P5.2 only reads its stored state and does
  not alter nonce issuance or consumption.
- Rollback is limited to the API agent surface, its read-only P5 status seam, tests, configuration names,
  scaffold assertions, and documentation. P1–P5.1 and P6 remain unchanged.

## Decisions / deviations

- The agent lives inside `apps/api`, the existing orchestration boundary, instead of creating a new package.
- The original provider adapter used a Responses API over `fetch`; it has since been replaced by the
  official Gemini SDK in P15. Tests use
  an explicitly injected scripted provider, never an automatic production fallback.
- A prior independent review found that free-form request text could leak to provider/audit and a
  negated second target could evade alias containment. The final design accepts only whole forms
  generated from public catalog aliases, discards raw text, and checks that the
  first model call resolves to the host-selected entry.
- The agent route prepares only. Authorization status is a separate read-only lookup after the browser P5
  flow, preserving the asynchronous human boundary.
- No live registry write is authorized by P5.2, so valid-flow evidence is local deterministic integration and
  must not be described as a live Sepolia clearance.

`CLEARANCE_NOT_FOUND`; it is not positive live clearance evidence.
